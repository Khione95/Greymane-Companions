===== research:switch
SUMMARY: I could not pin the Kliff refusal on one check from static analysis alone. What the code does settle is that the plugin's own Kliff entry is not the problem. The switch never reads the actor key from that entry. It reads Kliff's actor straight from the owner: [owner+0x60] at 0x17ED0A5 on the server side of the check and 0x4FAAEB on the client. The owner does not change on a focus change; only user+0xD8 does. So the key can never go stale. The entry is also byte-for-byte what the vanilla quest stage 0x293DDE0 creates, and no switch check reads its type or its position in the list.

**How a switch runs:**
- The client UI first runs a shared yes/no check (0x17EC980, which calls 0x17ECB50 for the target).
- The client then sends 0x8F0 StartChangeFocusActorReq {u32 target key, u8 force}. The server runs the same check again (0x294D5B0).
- The client sends 0xA9A ChangeFocusActorReq. The server (0x294C610 → 0x28F82A0) picks one of two paths: "target is in the party" (just swap control) or "target is not in the party" (bring the target over, then re-apply the remembered list).

**What is different for Kliff:**
- He has no mercenary record, so the game never re-summons him. Damiane and Oongka are summoned next to you when missing; Kliff must already be valid where he is. On the server that failure is eErrNoFailToSummonMercenary. On the client it is the actor lookup 0x8AE940 failing, which gives eErrNoInvalidFocusActorKey.
- His cooldown is the clan+0x88 entry with mercenary number -1, not a per-mercenary entry.
- A special character index (global +0x10A) skips the "target must be in the party" rule and the distance rule. Kliff is very likely that index, but this needs a runtime check.

**What can block only Kliff (most to least likely):**
1. He is out of reach or not valid where he is: he did not follow your new character, so the client no longer has his actor; or he is downed (cc+0x273), dead, or his AI is busy (0x1F5ABC0).
2. His -1 cooldown entry is running or stuck. An entry with +0x18 non-zero never counts down.
3. His character key is in the remembered list clan+0xE8 (refusal slot 0xEC). The server log showed remembered 0 on the server, so the client's copy would have to differ.
4. Only if +0x10A is not Kliff: the party list is non-empty and has no Kliff entry (slot 0xE6), or, on the client, he is in the list but far away and off screen (slot 0xE4 or 0xEA).
5. A data-driven block list for the field or region (slot 0xD4).

**How the plugin could contribute:**
- Register passes the current control character's key. If you recruit while playing Damiane, she gets an entry and Kliff gets none. That only matters in case 4.
- RemoveAccompany removes the control character's own entry when it is the only one left. It then runs 0x2152070 on the control character with r9b=1, which calls the safe-spot teleport 0x2B98E20.
- Any explicit-key AccompanyMercenary call clears the remembered list (0x2150A59).

**Repair:** one server-thread call to AccompanyMercenary with keys {owner key, control key, every current entry's key}. It is idempotent. It clears the remembered list, creates Kliff's entry if missing, re-arms his actor, and resends the full list. The client then replaces its list and zeroes its remembered count (0x9E46F0). This fixes cases 3 and 4 and any client/server mismatch. Being out of reach is fixed by teleporting Kliff to the control character; a cooldown or a downed Kliff by waiting.

**Diagnostic:** log only. In H0, log every 0x8F0, 0xA9A and 0x84A packet with its target key and the returned error. If no 0x8F0 for Kliff's key appears when you try, the client refused. Then add a log-only detour on 0x17EC980 that records the returned message slot. That names the failing check in one test.

===== research:dismiss
SUMMARY: Why you can't switch back to Kliff: the game has its own rule for this. While your party list (the accompany list) has anyone in it, you can only switch to a character who is in that list. Damiane and Oongka are in the list, so switching to them works. Kliff's own list entry (the owner entry) is evidently gone, so the game blocks him with its 'not accompanying' reason. Dismissing Luceran did not help: Damiane and Oongka keep the list non-empty, and Kliff is still not in it. The check is shared code run by both the companion quick-slot screen and the server's pre-check, and Kliff gets no exception: the only skip is for the game's 'WorldObserver' character, while Kliff is 'MainCharacterKey'.

What removed Kliff's entry is not proven. The log has no plugin action at that time. The list went 3 -> 2 at 16:09:24, about 5 s after what looks like your switch to Damiane at 16:09:19 (you jumped 41 m and Luceran was caught up to you). Kliff's entry is the likeliest one dropped there, but that is an inference. The plugin also has a latent bug of the same kind: Register and Recover pass the character you control as the first key, so recruiting while you play Damiane would never put Kliff in the list.

The fix is a small pump guard. While you play someone else and the list is not empty, if Kliff's entry is missing, put it back with AccompanyMercenary(clan, &err, {Kliff's key}). This is the same owner entry the game itself makes, and it sends the full list to the client, so the switch check passes again. Kliff then follows the character you play, the same way vanilla keeps Kliff in the party after a switch. A log-only probe on the check function will confirm which reason blocks him.

Why Luceran vanished on Dismiss: the removal function always calls the 'move to a safe spot' teleport, with the 'teleport' flag hard-coded to 1. The search box is centred on his own position, and the spots it returns can be about 200 m away; the plugin's own rescue log shows 190-210 m. So the server moved him out of sight. On the client those clan steps do nothing, and his chart does not teleport him home either. To make him walk home: skip that one teleport during the plugin's own Dismiss call (patch one slot in the server clan's table of functions), then restart his client-side AI with the existing Resync so his camp schedule takes over. Riding home is not possible, because camp comrades have no horse records.

2. Kliff's actor is not loaded on the client: eErrNoInvalidFocusActorKey at 0x4FABFA. No packet is sent, and the predicate never sees it.
3. EC: Kliff's key is stuck in the client's or the server's remembered list. This happens after a failed re-apply, or when the client dropped a 0x9FB update because one entry had actor 0 or index 0xFFFF (0xBEC2D0).
4. D4 / DE / DC on Kliff:
   - D4: his AI is busy (0x1F5ABC0), or he is on a block list.
   - DE: he is downed.
   - DC: an owner cooldown entry with merc -1.
5. Server owner path: owner->vt+0xC0(4,0x10) fails, giving eErrNoFailToSummonMercenary (0x28F8DDB).
