Two corrections to the research came out of this:
- MAP: in 0x9E8D10 the 5th argument means "explicitly no icon", not "decided". 0x9E90AA writes 1 there together with tex = 0xFFFF; 0x9E9FDB (the hide path) writes 1. The caller 0x9E89C0 skips its fallback when that flag is set (0x9E8BF1). The detour must never set it. The research's "*decided = 1" would hide the icon.
- MAP: the two "deliberate no-icon" exits in the mercenary branch are static npcInfo flags, not cutscene hides. 0x9EA0B0 tests npcInfo(+0x6C)+0x1C bit 0 (0x9EA0FF). 0x9E9A29 tests bit 0x20. [0x6CF7144] is the error constant eErrNoInvalidNpcInfo, used only as a nonzero value. So overriding them for recruited comrades is what we want.

  static bool SwapSlot(uintptr_t slotRva, uintptr_t expectRva, void* detour, void** original, const char* name)
  {
      void** slot = (void**)(g_base + slotRva); DWORD old;
      if (*slot != (void*)(g_base + expectRva) || !VirtualProtect(slot, 8, PAGE_READWRITE, &old))

      return true;
  }

1.2 Detours (they run on whatever thread runs the chart). For client-run comrades that is the client AI update (0x8BE850 -> 0x91ADA0 -> 0x2070760, or the event handlers). For a server-run AI it is the server thread. Never inside the plugin's own calls.

  static CondEvalFn g_condOrig[7];
  static volatile LONG g_hidden[MAX_COMRADES], g_hiddenCount, g_condForced[7];

  static __declspec(noinline) uintptr_t RunnerAi(uintptr_t runner)  // [[runner+0x68]], as CheckAccompany 0x22EA744..0x22EA74B
  { __try { uintptr_t h = R64(runner + 0x68); return h ? R64(h) : 0; } __except (EXCEPTION_EXECUTE_HANDLER) { return 0; } }

  static __declspec(noinline) uint32_t AiKey(uintptr_t ai)  // [ai+8] = actor, actor+0x60 = key
  { __try { uintptr_t a = ai ? R64(ai + 8) : 0; return a ? R32(a + 0x60) : 0; } __except (EXCEPTION_EXECUTE_HANDLER) { return 0; } }

  template<int I> static uint8_t __fastcall CondDetour(uintptr_t self, uintptr_t runner, uintptr_t ctx)
  {
      uint8_t r = g_condOrig[I](self, runner, ctx);  // the original first, as vanilla; its answer is also research data
      if (!g_hiddenCount) return r;                  // fast path: one load when nobody is hidden
      uintptr_t ai = RunnerAi(runner);
      uint32_t key = AiKey(ai);
      if (!key) return r;
      int slot = -1;
      for (int i = 0; i < MAX_COMRADES; ++i) if ((uint32_t)g_hidden[i] == key) slot = i;
      if (slot < 0) return r;
      uint8_t f = COND_SLOTS[I].forced;
      if (r != f) { InterlockedIncrement(&g_condForced[I]); NoteCond(I, self, ai, r); }
      return f;
  }
  static void* const COND_DETOURS[7] = { (void*)&CondDetour<0>, ..., (void*)&CondDetour<6> };

The skeptic's crash concern: 0x20B/0x21A/0x21B/0x230 never read rdx themselves. The chain is the game's own (CheckAccompany, SpawnAction 0x22E4727, departure 0xEBD4186), but it may not be valid for every one of the 24 evaluator callers. So it is read only after the g_hiddenCount fast path and only under __try. Do not require an exact AI vtable: a subclass would silently turn the feature off. NoteCond records the vtable instead (1.5).

The key read on the client actor matches the server actor's key. The plugin already relies on that: c->selfKey from the client root is looked up on the server, game.cpp 464/475.

SUMMARY: TRACK sched: what it takes to make a recruited camp comrade drop his NPC-schedule task at once. This was static work only. Nothing in the game was run, and no project files were edited. Scratch scripts are in <scratchpad>\gca\wf8\sched\ (myvtof.py finds a vtable from an RTTI name, vtd.py, callers.py, nest.py prints a nested chart container, morrow_states.py, pk_of.py, where2.py).

RESULT. The CheckToDepartureNextNPCSchedule check is not a timer. On every chart update it recomputes, from the game clock, which schedule slot should be active (0x20863A0 -> 0x1815E40). It reports true when that slot differs from the current slot. Its body is protected (.xtls 0xEBD4180). It is reached only through a 5-byte jmp stub at 0x22E38B0, and the only reference to that stub is its vtable slot at 0x58C01A8. CheckExistNPCScheduleInfo is the same: body .xtls 0xEBCE770, stub 0x22E3200, slot 0x58C2208.

Condition results use 0 = TRUE, 1 = FALSE, 2 = undecided.

Making departure true is not enough on its own. After the end animation the re-decision (WaitPackage InitLogic #0x334, CommonMoveFindPackage InitLogic #0x246, NPCScheduleEndAction #0x2FE, MoveEndLogic #0x2B2) still prefers the schedule: walk back to the spot, re-enter ReadyToNPCScheduleActionPackage, and loop. None of these handlers tests the accompany type. Following comes only from the party / formation branches, which sit after the schedule branches.

So all schedule conditions must answer 'no schedule' for a recruited camp comrade, except departure, which must answer 'go now'. That makes his chart behave like a summoned (spawn 0xE) copy, which already follows at once.

===== research:map
SUMMARY: The game picks every actor's map icon in one plain client function: 0x9E8D10. Its only caller is 0x9E89C0, which runs from ClientMinimapActorComponent::update (vt 0x55BEC90 slot +0xF8 = 0x9E7C60; the component sits at [actor+0x68]+0x160) and from the periodic CachedMapIconInfo_updateTask (vt 0x55BB768, run function 0x94FB30). That function is the only map code that reads characterinfo _uiMapTextureInfo (+0x1E6), so Damiane's world-map and minimap icon both come from it.

Why Damiane and Oongka get an icon and comrades do not:
- **Damiane and Oongka** have _playerIndex 2 and 3 (runtime +0x104). That sends them down a separate branch (0x9E9191 to 0x9E9276): if they are a valid owned mercenary of the player's clan (0x214E7A0, record +0x28 != -1 and +0x20 != 0xFFFF), they show their own texture from +0x1E6. Damiane uses Actor_Player_Damian (key 0x13F7), Oongka uses Actor_Player_Oongka (key 0x13F8).
- **Camp comrades** have _playerIndex 0 and _spawnActorType 4 (Mercenary), like Damiane. Mercenary actors go to 0x9E99B1, which never reads +0x1E6. There the icon depends only on the mercenary record's state (0x214D130). State 1 (record +0xE2, the Follow-into-Combat flag) shows the generic Actor_Character icon. State 3 (+0xE4) shows Faction_OperationCharacterActor. Any other state shows nothing. The accompany list (clan+0xB8) is never consulted. Comrades also have _uiMapTextureInfo 0, which is not a valid key, so it reads back as no texture (0xFFFF).

So a characterinfo edit alone cannot give recruited comrades an icon, and certainly not one shown only while they accompany you.

Smallest working change: a client MinHook on 0x9E8D10 that changes the result afterwards. It is plain code with a unique 46-byte prologue. After the original call: if the result is "no icon", the icon was not hidden or removed on purpose, and the actor's key is one of the plugin's recruited comrades (g_tracked slots 0-3), set the texture to the game's Actor_Party_Default index. That index is read from UIMapTextureInfoManager+0x104. Actor_Party_Default is the game's own party-member icon: story Greymanes such as Macduff, Yann and Nairah carry it. Actor_Character (+0x100) could be an ini option; it is what the game shows for a Follow-into-Combat comrade, and 0x9EA6F0 attaches a label to it, probably his name. This covers camp actors and summoned copies, and the icon goes away by itself once Dismiss clears his tracked slot.

Both icons are in the same never-filtered UI filter group as Damiane's (uifiltergroupinfo Group_Invisible 0xF424F), so the world-map legend will not hide them. None of this has been tried in the game yet.

ACTION REVIEW: Safe in principle, but build it as a logging test first.

Safety checks:
- **Protected code:** 0x9E8D10 is plain code, not .xtls. Its prologue is unique and MinHook can relocate it.
- **Writes:** the detour writes only to the caller's stack locals (tex, decided). It calls no game function and writes nothing that could reach the save.
- **Threads:** it can be called from the minimap update, from the CachedMapIconInfo interleaving task (possibly a worker thread) and from a protected caller at .xtls 0x9C61E0B that the claims did not list. So keep it lock-free: read only g_tracked, wrap the pointer chain in __try, and never Log on every call.
- **Per-frame cost:** it runs once per actor per update. Test *tex == 0xFFFF && !*decided && !*removed before TrackedSlot, which loops over 8 entries; that is cheap.
- **TLS:** read the server/client flag exactly as game.cpp does (gs:[0x58] -> [0] + 0x1EC). Compare R64(m) with base+0x59881A0.

Fixes before shipping:
1. Skip dead actors (cc+0x273 != 0). The dead-body path at 0x9E9575 can leave tex 0xFFFF with decided 0, which would put the party icon on a corpse.
2. Decide whether the icon should stay during PHASE_STANDBY and PHASE_LOST. g_tracked keeps every phase except PHASE_FREE.
3. Accept that it overrides the game's own no-icon exits at 0x9E99C2 and 0x9E9A4F. Or, more conservatively, act only when the game reached the end of the mercenary branch.

Main open risk: nothing shows the selector is ever re-run for an actor that never had an icon. The per-frame update calls it only when comp+0x34 & 6, and those bits are written by the result applier 0x9EA6F0 itself. Otherwise it depends on the cached task's key list or the .xtls caller, and their membership is unknown. So the first build should log once per tracked actor key when the detour sees it, with its kind, the original tex, decided, removed and comp+0x34. If it never fires, hooking 0x9E8D10 alone will not work.

Note for later: for a party member that is not an owned mercenary of the clan, the game already shows Actor_Party_Default itself (0x9E92CA -> 0x9E9469). Comrades are owned (AccompanyMercenary requires it), so they bypass that path.
