===== dismiss
SUMMARY:
Dismiss needs a new data prompt and a small plugin step together. Data alone cannot remove her from the accompany list, and the vanilla Disband call is the wrong tool for a camp comrade.

(1) Why vanilla Disband is hidden. Npc_Order_Disband 0xF425B has no CheckAccompanyType at all. It needs two things a followed comrade never has:
- the player carrying the buff tag 0xC10DC139 (stored only in skill 11192 "Passive_FollowPlayer");
- CheckSameParty: she must be in the same Party as the player. The accompany list never adds her to a Party.
So it is an order for Party/escort followers, not for the accompany list.

How vanilla Disband works:
- Client: the mercenary quick-slot UI 0xEFD810 -> 0x6508A0 -> client clan 0x9DCC40 -> TrocTrDisbandMercenaryReq (packet 0x9C7).
- Server: handler 0x2A33000 -> DisbandByKeys 0x2BA10A0 -> 0x2151570 (flags 1,0,0,0).
- Because the first flag is 1, the game also sets her 0x100000 flag and queues an "unspawn" timer, ending in the game's logout 0x2068340. So vanilla Disband despawns her. She does not walk home.

The comrade charts' Disband event handler 0x21E is still not decoded. No AI function can remove a list entry anyway, so the event alone does nothing to the list.

(2) Recommended design: a data clone plus a plugin hook (your options a and b together).
- Data: a cloned prompt, "Npc_Order_Dismiss" 0xF5010, built from Npc_Order_Wait.
  - Label: the game's own "Dismiss" text, or "Disband" as the safe fallback.
  - Shows whenever she is in the list, any type (1 to 4).
  - Sends no AI event. Uses Follow's prompt key so it does not share Standby's.
  - It replaces Npc_Order_Disband in Test 3's comrade lists.
- Plugin: hook TryPreempt 0x2B36EF0 to catch the clone and queue it.
- Pump: remove her with 0x2151570(clan, &err, &{&idx,1,1}, 0,0,0,0), the same flags the game itself uses at 0x2BAEB00. Then restore her logout distance and stop looking after her.
  - Result: she is off the list and the client is told, the same way vanilla Disband does it. She stays hired. No disbanded flag is set and she is not unspawned.
  - Only for a summoned copy (spawn type 0xE) use DisbandByKeys, the vanilla unsummon, as for Damiane.
- Option c (forcing vanilla Disband visible with a hook on 0x21206C0) is rejected: it still removes nothing and sends the undecoded event.

(3) Whether she goes back to her routine by herself cannot be settled statically. Evidence that she should:
- AI charts test list membership (AICondition_CheckAccompany scans clan+0xB8).
- Aldric stayed on his camp schedule while he was in the list, as long as no Follow event was sent.
- The 0x100000 flag only filters AI events; it does not drive behaviour.

For her, the client copy of the list must update; that goes through the same protected sync vanilla uses. If she was dismissed far from camp, the restored logout distance lets the game's clean-up log her out, and the camp should spawn her again (not verified).

Fallbacks if she keeps following: a clone variant that sends the Standby or Disband event, or DisbandByKeys as a last resort.

About your note on the knowledge entry already showing their picture: that belongs to the HUD portrait work and was not covered in this run.

===== portraits
SUMMARY:
Each character's Knowledge entry links it to a picture through three tables (characterinfo, knowledgeinfo, stringinfo). The game follows the same three steps itself in its world-map and faction UI code. Every characterinfo record has a _knowledgeInfo field holding a knowledge key. That knowledge record's _uiTextureName field holds a stringinfo key, which is the hashlittle(text, 810718) hash of a texture id such as "cd_knowledgeimage_Knowledge_GreyFur_Max". The image file is ui/texture/image/knowledgeimage/<texture id in lower case>.dds, because the UI looks up textureid(...) by file name. I wrote portraits.py at scratchpad\gca\wf4\portraits.py. It follows that chain for the 43 roster.h characters plus Kliff 1, Damiane 4 and Oongka 6, and found a picture for all 46 (46/46). All 46 are 512x512 DDS in DXT1 (BC1) format with 1 mip, 131200 bytes each. The script also builds images from them: Pillow 12.1.1 opens them once the script's unpack_dds() has turned the archive's "Partial" DDS back into a standard file. `--out DIR --size 128 --jpeg` wrote 46 JPEGs of about 5 KB each (376K on disk), using the same flatten-to-JPEG idea as DLLCrimson's convert_icon in build_data.py. The decoded pictures are correct waist-up portraits on a grey background; I checked Max, Matilda, Damiane, Oongka, Ziane and Kliff on a contact sheet (wf4\contact.png). The full run output is in wf4\portraits_run.txt.

ACTION REVIEW:
Nothing proposed can unhire a comrade or break save loading. No DMM data is edited, and nothing calls DisbandByKeys 0x2BA10A0, SetAccompanyType 0x21523A0, Ack 0x297EF40 or the interaction step 0x211DA30. Action 1 ("no data edits") is correct.

Action 2 (build step) is read-only on the game. game_files reads the .paz files 'rb' through the Crimson Browser Sharp index cache, tables.py only reads, and portraits.py writes only under --out. I checked the existing output wf4\jpg: 46 files, 128x128, 3874-5500 bytes, 206,397 bytes in total (the claim said about 230 KB). My contact sheet wf4\sk\contact_sk.png shows 46 cleanly decoded, distinct portraits with no LZ4/DXT garbage, and the women are where expected (Damiane, Nairah, Matilda, Evelyn, Joan). The file names use the roster key, so the pictures are correct as long as the HUD looks them up by roster key.

Conditions:
(a) Look up portraits by the person's roster key, never through the chain on the live actor's own characterinfo record. If Approach A hires Yann's companion copy 0xF5235 (or 0x2 'Yahn'), the chain gives Kliff's picture. Map 0xF5235 and 0x2 to 0x192, and 0xF52CC to 0x19C (or show no picture). Keys not in the roster should show no image.
(b) These are game art files. Keep the generated JPEGs out of the GitHub repo, as with the Seasons rule of no game assets, and let the user decide whether to embed them in the release .asi. The alternative is to generate them on the player's machine.
(c) Re-run after game patches. The index cache must match the installed game; unpack_dds raises on a size mismatch, so a stale index fails loudly instead of producing a wrong image.

Action 3 (runtime alternative) is riskier:
(1) It has the same wrong-image problem for 0xF5235 and 0x2.
(2) It does not check that the u16 at kn+0x12 is not 0xFFFF. 1266 of 6713 knowledge records have a texture key missing from stringinfo, and the out-of-range getter path returns the default object at [0x6CFDED0] (see 0x433758, and 0x388E1F jae for stringinfo), so dereferencing +0x18 then * may crash. Check for 0xFFFF and for a null pointer.
(3) charHandle must be the u16 table index the plugin already passes to g_charInfo (CharKeyOfIndex), not the u32 key.
(4) The getters deserialize records lazily on first access (0x4336BF-0x433725). Call them only from the thread the plugin already uses for g_charInfo.
(5) Vanilla shows Unknown_Portrait until the player has learned the knowledge entry (0x652F40 gate at 0xF1655D; per-player value at 0xF60FF7). Showing the real picture regardless is harmless for recruited comrades.
(6) It yields only a texture id, so a D3D/ImGui HUD still needs pixels. The build-time route is the right choice.
